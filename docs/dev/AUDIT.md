# Project audit

Audit baseline: `f32e41d` (2026-10-03). Scope: all application modules, packaged assets, dependency metadata and lock, Docker/Compose/Make, CI/release workflows, documentation, and test strategy.

## Delivery

The audit produced two independently reviewable branches based on the same baseline:

- Runtime correctness: configuration and room contracts, state/credential durability, passage and delivery validation, lifecycle cleanup, logging, service rendering, and packaged resources.
- Development and deployment: locked uv environments, pip/pipx compatibility, Docker/Compose fixes, release validation, and contributor/user documentation.

The branches merge cleanly. Startup test network isolation is shared between the branches so each test suite is independent of GitHub availability. Changes are committed by concern, with regression tests and behavior documentation accompanying the implementation.

## Findings and resolution

| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| State migration   | A successful move to staging followed by failed publication deletes the only copy of an E2EE store. A competing target can trigger the same deletion.                                                                                                                                                                                                                            | Restore moved state on failed publication. Preserve partial moves and refuse unresolved staging on restart instead of opening an empty store.                                                                                                                                         |
| Authentication    | Credential persistence suppresses replace failures, so login can report success without saving a session. Temporary writes can leak files. Reserve at least nine characters for message text, truncation, and the mandatory suffix.                                                                                                            |

## Contracts to preserve

- `biblebot` and `python -m biblebot` remain entry points; pipx installs normal Python distributions.
- KJV requires no API key; ESV requires a non-empty key. Passage lookup returns `(non-empty text, str | None)` or raises a documented exception.
- Only whole-message scripture references from configured rooms, other senders, and events after startup trigger replies.
- Room aliases resolve to canonical IDs; the admission list and join list use the same identifiers.
- `BIBLEBOT_HOME` takes precedence over XDG configuration/state homes. Moving state must never discard the only copy of keys.
- Cross-signing remains an explicit command with refusal checks. The audit does not rotate identities or contact a live account.
- Message sends inspect nio ErrorResponse return values; Matrix failures and transport failures remain distinct.

## Review and operational limits

Unit tests use mocked Matrix clients. Package and container smoke checks exercise imports, entry points, bundled assets, and crypto availability; they do not prove delivery against a real homeserver. Live encrypted-room exchange and cross-signing require a dedicated account and must be checked before deploying provider changes.

The broad synthetic pattern tests remain for compatibility. Replacing them requires deciding which operational scenarios deserve real integration fixtures; adding more synthetic tests would not establish those guarantees.

## Further work

- Add a dedicated homeserver integration fixture for encrypted exchange, alias joining, retries, and cancellation using the real nio provider. Mock-only suites cannot establish these guarantees.
- Replace synthetic pattern tests gradually with observed application scenarios. Keep focused regressions for the shared configuration, passage, room, and resource ownership contracts.
- Consider extracting the message delivery orchestration from the large bot module when additional behavior requires it. The shared configuration/room/formatting seams provide a smaller surface for that work; a speculative framework is unnecessary.
